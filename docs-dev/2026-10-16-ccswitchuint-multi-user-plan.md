# ccSwitchUint 多用户改造计划与可行性分析

日期：2026-10-16。本文是基于当前仓库的设计方案，尚未实施、部署。

## 1. 目标与架构结论

将现有 cc-switch-web 改造成多用户聚合网关：用户管理自己的供应商和官方账号，按规则共享资源；消费者选择获准使用的模型，通过个人设备密钥访问统一代理；平台按调用者、资源提供者、实际账号分别统计和执行额度限制。

保留 Rust/axum、React、现有协议适配、模型目录和远程安装脚本。身份、授权、额度账本、账号调度需要新增；当前以设备为单位的管理状态需要拆分。这是服务端领域模型的改造，无法仅通过增加登录页面实现。

单实例起步可以继续使用 SQLite，但现有连接由全局 Mutex 保护，额度预留、写日志和查询会争用同一连接。应保持事务短小，避免持有数据库锁等待网络，按实际并发验证吞吐；多实例和更高并发再评估 PostgreSQL。SQLite 并不自动解决进程外缓存和分布式限流问题。

## 3. 统一身份与权限

平台角色先保留管理员、普通用户两种。供应商提供者是某项资源的所有者，同一用户可以同时是消费者和多项资源的所有者，无需另设固定的“提供者角色”。

网页采用服务端会话与 HttpOnly Cookie，密码保存 Argon2id 哈希。包含注册、登录、退出、修改密码、会话撤销、禁用用户和管理员重置密码。注册可配置开放、邀请或管理员审批；新注册用户默认不能管理平台。初始管理员通过部署初始化创建，避免将公网第一位注册者自动提权。

命令行使用个人 API Key，可按设备创建、命名、撤销、设置范围。服务器保存随机高熵密钥的哈希和显示前缀，明文仅创建时返回。模型目录读取、代理调用和网页管理权限分开。个人 API Key 不作为全站管理密码。

Web 和代理鉴权都生成可信 `RequestContext`，至少含 `consumer_user_id`、`api_key_id`、`device_id`、角色与权限范围。DAO/服务层显式接收访问范围；不能信任客户端传入的 `user_id`。后台任务使用显式系统身份和资源归属，不能靠“无用户”绕过权限。

HTTPS、允许的网页来源、Cookie/CSRF 配置和可信反向代理头一起落地。当前宽松 CORS 和共享密钥登录不能原样用于多用户 Cookie 登录。FRP 继续承担转发，外部域名和代理基址通过管理员配置，避免由任意 Host 头生成含密钥的接入命令。

特别处理现有本地文件功能：所有网页用户仍共用一个服务器 OS 账号。按网页用户分组展示，不能隔离对同一个 `~/.codex` 或其他工具目录的写操作。远程用户的配置通过导出脚本在各自机器写入；服务器本机接管、文件修改和终端功能归入运维后台。若以后开放用户文件工作区，需要用户独立目录、路径校验和执行隔离。

共享供应商列表使用单独的公开 DTO，不返回 `settings_config` 原文、API Key、OAuth token、完整配置或任意上游错误正文。供应商所有者查看他人消费时默认仅见计量元数据，不见对话内容。

## 5. 供应商所有权、共享规则与限额

供应商、官方账号均增加 `owner_user_id`。发布到聚合池为资源级开关，只能由所有者操作；管理员可执行独立的停用操作并留审计记录。消费者只选择使用哪些模型，不能替其他人操作入池开关。

共享规则明确拆为两部分：

1. 可用范围：默认所有已激活注册用户；也可设为仅自己、指定用户。
2. 使用额度：公开默认额度与指定用户覆盖规则，支持请求次数、token 或平台点数，并支持周期、有效期、模型限制、速率和并发限制。

“公开”仅决定默认授权范围，不自动表示无限额度；具体默认数量由提供者设置。所有者本人默认不受自己配置的分配额度限制，仍记录其实际用量，并受上游实际额度和平台服务保护限制。

单独记录资源共享总预算和每用户预算，防止给十个人各分配额度却超出提供者愿意共享的总量。建议对公众使用按请求占用剩余预算；对明确承诺的保留额度提供后续扩展，避免混淆“可用上限”和“独占预留”。

个人额度、资源共享总预算、平台额度、设备范围、模型权限在每次请求时同时校验。适用的任何限制耗尽，都不能因选择另一个账号绕过。权限和配额调整只影响后续授权，不重算已结算历史。

## 6. 聚合模式与个性化模型命令

服务端只开放聚合入口，移除默认供应商的 UI、隐式回退与相应后台控制接口。保留稳定供应商 key，未知或无权使用的 key 直接返回结构化错误。

用户可选择的模型为：已发布资源 ∩ 授权允许的资源/模型，再合并官方池的可用模型。用户勾选模型并保存为个人配置，可创建多个配置集。临时额度耗尽显示状态；永久撤销权限从后续目录移除。客户端旧目录即使保留某个模型，网关仍按实时规则拒绝。

生成命令使用该用户的设备密钥，目录只包含用户选择且仍获授权的模型。现有安装器的备份、原子写入、可选 daemon 重启可以沿用；增加新设备接入步骤，负责写统一代理地址及个人凭据，日常模型更新只刷新目录与相关选择。

下载权限和执行时第二次下载目录都需要验证设备身份。命令、脚本和响应不得带管理员共享密钥或上游凭据；含个人密钥的响应禁止缓存，日志脱敏。也可采用短时接入票据交换设备密钥，但不得把一次性票据误当作脚本两次下载都能使用的长期凭据。

“不设默认供应商”仍允许用户选择客户端启动模型。Codex 配置中的 `model` 是个人启动选择，和服务器默认路由不同。

## 7. 官方账号池与跨提供者切换

必须区分平台用户、上游官方账号和逻辑模型入口。当前 `ccs-供应商key/模型` 指向一家；如用户选择这个精确入口，不应悄悄改到另一家。官方自动切换应新增稳定的逻辑池入口，例如 `ccs-official/gpt-…`，池下才是不同所有者自愿共享的官方账号。无需恢复之前的手工模型映射池。

候选账号必须同时满足：所有者已发布/同意入池、当前消费者获授权、该模型及能力可用、个人与共享预算可用、凭据有效、未处于限流冷却且并发许可足够。不能把“所有平台用户的所有官方账号”直接作为候选。相同真实账号的重复绑定应识别和合并，防止重复计量与令牌刷新竞争。

建议调度优先顺序为用户自有可用账号，再在其他获授权账号中按轮询选取；用户自有额度耗尽也可以转入获授权共享池。也可在后续添加贡献权重，首版先保证可解释的顺序和轮询公平性。每次尝试写入实际账号与提供者，最终请求归消费者，资源支出归实际提供者。

错误分类：

- 明确额度耗尽：暂时移出候选，记录窗口与恢复时间，尝试下一获授权账号。
- 短期速率限制：按重试提示冷却，不等同于余额为零。
- Refresh Token 失效：标记需要所有者重新登录，后台无法凭空恢复授权。
- 模型订阅权限不足：按账号和模型排除，不能据此禁用全部模型。
- 其他认证、网络或上游错误：分类处理并限制尝试次数，防止刷新风暴和无限轮询。

上游官方额度接口可能只能返回窗口剩余比例，甚至暂时不可用，因此“预知精确还能用多少 token”不能作为承诺。结合接口状态、错误响应和冷却实现调度，未知状态明确显示未知。

涉及 `previous_response_id`、服务端会话或其他账号绑定状态时保持账号亲和性，并验证连续对话是否允许切换。已向客户端发送输出后不能透明重放；连接异常但上游可能已执行的请求也不能无条件重试。首版将可安全切换限定为明确失败、尚未输出且可重试的请求。

## 8. 使用统计、计量与额度账本

使用统计是核心改造，不作为最后补充的页面功能。每条请求至少记录：

- 调用者、API Key、设备、逻辑请求 ID。
- 资源提供者、供应商、实际官方账号、账号池与每次尝试 ID。
- 客户端选择模型、实际上游模型、协议、开始时间、首 token 延迟和结束状态。
- 输入、输出、缓存、可获得的其他 token 字段；上游 usage 原始语义和来源。
- 上游成本估算、平台扣减额、价格版本、额度规则版本及结算状态。

统计提供三种视图：消费者看“我用了多少”；提供者看“我的资源被谁用了多少”；管理员看平台消费与供给全貌。一个请求有消费者和提供者两种观察角度，不能相加为两次平台调用。

现有汇总、趋势、模型/供应商统计、热力图、请求分页、单条详情、数据源查询、CSV/其他导出全部按服务端授权范围查询。历史日汇总至少按日期、消费者、提供者/资源、模型分组，账号维度按运维需求保存。统一明确账期时区，避免用服务器 localtime 意外改变用户周期。

请求数量缓存、前端查询缓存、下载缓存、目录缓存和模型健康缓存都要审查。授权相关缓存键必须包含用户/权限范围和必要的权限版本；登出、切换用户时清理前端缓存；账号健康按真实账号隔离。现有日志指纹去重和请求 ID 冲突处理同样需要身份维度，不能把两个用户的相似调用合并。

区分三个概念：上游余额/订阅窗口、平台分配额度、使用成本估算。现有 `src/components/quota/` 主要展示上游订阅额度，不能直接作为新用户预算账本。官方订阅没有逐次 API 发票时，费用明确标注估算或使用平台点数，价格由受控版本决定；缺失价格不能默认为免费。

配额执行采用持久化状态机：创建请求记录 → 原子预留所有适用预算/并发许可 → 选择账号 → 调用 → 根据实际 usage 结算并释放预留。事务不跨网络等待。请求 ID 和结算键由网关控制，结算必须幂等；多次上游尝试关联同一逻辑请求，分别记录实际资源消耗，防止重试导致用户重复扣款。平台自身重试损耗的承担规则应明确，不能悄悄混入两次用户成功调用。

请求次数和并发可以实现确定性硬限制；token/费用通常在返回后才准确。首版使用在途预留与请求上限控制超额窗口，不声称所有上游都能做到精确到 token 的绝对硬上限。中断且无法获得 usage 的请求保留待核算状态，按明确规则对账；不能直接记作零。服务重启后恢复或核对悬挂预留，避免所有额度永久锁死或直接返还造成超用。

额度账本独立于可清理日志。清理日志、压缩日汇总、修改价格、重新导入会话或删除用户不能返还已结算额度。历史价格快照用于维持历史一致性，金额/点数使用定点或整数表示。

本机会话日志用于诊断和补充个人统计；不能作为共享网关的额度扣减依据。现有后台扫描 moss 文件无法代表 nccl5 或其他用户的全量调用。若以后允许用户导入自己的日志，需要独立归属、可信度标记和按用户去重，只由网关确认的实际转发记录参与平台结算。

## 9. 数据模型建议

| 数据 | 建议结构 |
| --- | --- |
| 用户与身份 | `users`、`web_sessions`、`api_keys`；设备可独立表或首版作为密钥元数据 |
| 资源归属 | 扩展 `providers`；官方账号元数据增加所有者，敏感 token 独立存储 |
| 发布与授权 | `resource_publications`、`resource_policies`、`resource_grants`，支持公开规则与个人覆盖 |
| 个性化目录 | `user_model_profiles`、`user_model_selections`；资源模型清单另存 |
| 官方池 | `account_pools`、`pool_members`、账号健康/冷却状态、必要的会话亲和记录 |
| 额度 | `quota_buckets`、`quota_reservations`、`quota_ledger`，保留账期、规则版本和幂等键 |
| 请求与统计 | 扩展 `proxy_request_logs`，新增 `request_attempts`，重建带归属的日汇总 |
| 设置与审计 | 分离 `platform_settings`、`user_preferences`；新增 `audit_events` |

表名是设计建议，不要求机械增加所有表。原则是区分消费者、所有者、真实上游身份，以及平台级和用户级数据。不要给所有全局表盲目增加一个 `user_id`，也不要为每个用户复制整套服务器运行时。

## 10. 其他必须同步改造的范围

- 全量 API 清单：每个路由标记公开、本人、资源所有者或管理员；详情、删除、批量操作和下载遵循相同规则。通过隐藏按钮不能代替后端校验。
- 模型拉取、测速和余额脚本：使用所有者凭据，限制调用范围、频率与资源消耗，记录触发者；不能允许调用者拿他人凭据测试任意 URL。自定义 URL/脚本需有出站、超时与资源控制，管理员按部署需要配置允许范围。
- OAuth：登录流程、回调 state/PKCE、轮询任务和账号删除绑定发起用户；其他用户不能接管正在进行的授权。
- 后台任务：模型同步、账号刷新、额度刷新、日志压缩、定价同步区分系统任务与资源任务，保留归属、失败状态、重试与审计。
- 导入导出：普通用户仅导出自己的非敏感配置或本人凭据范围；不能下载全库 SQL。导入不能覆盖他人 ID、所有者、授权或账本。全库恢复和 WebDAV 全量覆盖仅管理员执行，并防止恢复旧快照重置当前额度/密钥状态。
- 删除与撤销：用户停用、资源撤回、API Key 撤销及时影响后续请求和缓存；历史记录保留稳定归属快照，账号移交不改写历史消费。
- 事件和日志：实时事件按权限分发；错误正文、请求头、token 和接入命令脱敏。消费者收到明确的未登录、无权使用、个人额度耗尽、资源预算耗尽、无可用账号等错误码，不暴露其他人的私密账号状态。
- 前端：普通用户保留模型、接入、我的用量、我的资源、个人设置；资源页增加共享和用量；管理员独立管理入口。多用户化同时减少桌面端操作对普通用户的暴露。

## 11. 迁移与实施顺序

现有数据先创建管理员归属，迁移供应商、官方账号及稳定 key。历史日志缺少可信用户信息，标为迁移前历史，不能凭空拆到各个新用户。设备级 `live-state.json` 中的聚合成员迁成资源发布状态；客户端文件写入状态留在设备层。

按用户此前要求，固定旧密钥不主动轮换。建议将旧密钥绑定到专用 `legacy-client` 身份，保留其现有客户端调用和目录更新范围；它不继续充当全体用户共享的管理身份。旧密钥产生的使用量统一归该身份，无法识别实际个人；后续给 moss、nccl5 创建个人/设备密钥后才有准确归属。管理员网页登录迁移到独立会话和密码。

推荐按依赖顺序交付：

1. **权限底座与迁移**：用户、会话、设备密钥、统一请求身份、所有路由权限清单、服务器管理能力隔离。此阶段新增用户不能直接访问未改造接口。
2. **资源共享与身份化计量**：供应商/官方账号归属、公开/指定共享、入池开关；请求身份从代理入口贯穿日志、汇总、导出、缓存和后台任务。先完成统计归属，再启用收费或额度扣减。
3. **个人聚合接入**：数据库发布状态、用户模型选择、个人目录、安装/更新命令；移除默认供应商及其隐式回退。
4. **限量服务闭环**：原子预留、结算账本、个人和共享预算、请求次数/速率/并发、缺失 usage 对账、进程重启恢复，以及三种统计视图。
5. **官方账号池**：获授权候选筛选、账号轮询、额度恢复、模型资格和会话亲和；按真实上游行为验证切换边界。
6. **整体收尾**：剩余 MCP/Prompts/Skills 等功能的用户范围或管理隔离、备份恢复语义、权限审计、迁移与回滚演练、多人并发验证。

阶段 1—4 形成可使用的多用户限量聚合平台；阶段 5 完成官方账号自动接续。不能先公开注册，再逐个补接口隔离。

## 12. 验收与可行性边界

- A 可使用 B 公开资源，但看不到 B 的密钥、OAuth token、其他人的对话或整库备份；B 可限制/撤销 A，网关及时生效。
- A 与 B 的用量、趋势、详情、导出、缓存和日汇总分别正确；提供者视角与平台总量不重复累计。
- 同一用户多台机器能按设备区分，并合并执行个人额度；并发不能重复占用最后一份额度。
- 重试、中断、usage 缺失、日志清理和服务重启不会重复扣款、直接免费放行或错误重置额度。
- 用户只能导出有权使用且自己选择的模型；修改客户端目录不能绕过服务端授权。
- 官方账号耗尽后仅切换到明确获授权且模型适用的账号，能够追踪实际提供者；凭据失效账号等待所有者重新登录。
- 已输出内容的请求不透明重放；依赖上游账号状态的连续对话保持可解释的行为。
- moss/nccl5 在身份迁移期间仍能访问既有服务，随后用各自密钥获得准确归属。

整体可行性高，主要工作量在全链路归属、并发额度账本和官方账号调度。现有协议适配、OAuth 刷新与模型目录可以复用；精确官方剩余额度和所有会话条件下的无感账号切换取决于上游能力，必须作为受约束功能验证。当前先落地方案，没有执行代码修改、服务部署或实现测试。
